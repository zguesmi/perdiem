# The enclave books the winner with the supplier's own credentials

The winner used to post its own proof of delivery: `keccak256(bookingId)` through `submitReceipt`,
which released its Stake. The contract checked nothing about that value. Any 32 bytes released the
Stake, so the proof cost a winner nothing to fabricate and the whole delivery phase was theatre.

The contract cannot fix this. A booking lives on a supplier's API, and no on-chain rule can read it.
Whoever reports it is trusted.

So report it from the party that is already trusted for the winner and the payout. The Enclave books
the winning bid itself, reads the booking id back, and carries it in the same Settlement that pays.
The contract refuses a settlement that names a winner without a booking id. Nothing moves on a
supplier's word.

Booking needs the supplier's credentials, so each Sealed Bid envelope carries `bookingUrl` and
`bookingApiKey` beside the salt. They are not fields of the `Bid` type, so they never reach
`hashStruct`, and the envelope is sealed to the enclave public key, so no rival and no node operator
reads them.

## How the write stays safe to repeat

A booking call is not a read. If the handler runs on several nodes, or a run is retried, or a cron
tick re-fires, a naive `POST` books the same room several times.

`clientReference` is set to the `auctionId`, which every node derives identically. The first book
lands. Any repeat is refused with code `4005` in 190 ms. The handler then throws away what the write
returned and reads the record back with `GET /bookings?clientReference=`, so the value that leaves
the Enclave comes from a read that is identical everywhere. Row V14 measured all of it.

The search cannot be skipped. `prebook` takes an `offerId`, only `POST /hotels/rates` mints one, and
an `offerId` goes stale in minutes, so the Bid cannot carry one either.

## Consequences

The delivery phase leaves the contract. `submitReceipt`, `slash`, `receiptDeadline`,
`RECEIPT_PERIOD`, `stakeReleased` and `stakeSlashed` are gone, and "Every USDC in and out" drops
from five rows to four. The Stake stops being a delivery penalty and becomes an anti-spam bond that
always comes back.

Suppliers stop booking. An agent has nothing to do after `bidDeadline`, which removes the demo's
only step that depended on a losing agent staying alive.

The enclave private key now opens booking credentials, not only bids. Whoever holds it can spend on
three supplier accounts. So the keypair is generated by an independent party, neither the buyer nor
any supplier, and only the public half is deployed. The enclave cannot generate it itself: it has no
randomness, and `x25519.utils.randomPrivateKey()` throws `crypto.getRandomValues must be defined`
there.

`bookingUrl` comes from the supplier, so a supplier can point the Enclave at a server it controls
and be handed a booking id it invented. That buys it nothing the Bid did not already buy: the
attributes were self-attested from the start, per
`docs/adr/0004-bid-attributes-are-self-attested.md`. It is the supplier's own booking to fake,
against its own stake and its own name.

A booking that fails costs the auction. No booking means no winner: the Payout Cap and every Stake
go back, and the Enclave does not fall through to the second-best bid. Falling through would mean
scoring one auction twice against one Policy, and a second booking attempt inside the same run
against a 10 s per-request timeout.

The Enclave now holds a payment-capable credential for the length of one handler run. That is a real
increase in what a compromised enclave is worth, and it is the price of a proof the contract can
refuse.
